# Правила совместной разработки

## Перед началом работы
- Выберите задачу и создайте ветку от актуальной основной ветки.
- Уточните, какой контракт использует модуль.
- Если требуется изменение контракта — сначала создайте issue/обсудите изменение.

## Именование веток
- `feature/<module>-<short-name>` — новая функциональность.
- `fix/<module>-<short-name>` — исправление.
- `experiment/<module>-<short-name>` — исследовательский вариант.
- `docs/<topic>` — документация.

## Pull request должен содержать
- Что изменено и зачем.
- Какой контракт реализован.
- Результаты тестов.
- Известные ограничения и условия, в которых решение проверялось.
- Сравнение с текущим вариантом, если это альтернативный алгоритм.

## Критерии готовности
- Реализация соблюдает публичный интерфейс.
- Контрактные тесты проходят.
- Нет аппаратных зависимостей в чистом алгоритмическом коде.
- Ошибки и тайм-ауты представлены явно.
- Обновлены README/документация при изменении поведения.

## Код и данные
Не коммитьте виртуальные окружения, логи, кэши, веса моделей и секреты. Для крупных моделей согласуйте Git LFS или внешнее хранилище.
