# Autonomous Drone System — Team Repository

Шаблон репозитория для разработки автономной связки **Scout Microdrone → Rover → Striker Microdrone**.
Репозиторий предназначен для хранения, совместной разработки, сравнения и интеграции альтернативных модулей.
Веб-симулятор используется отдельно; SITL, симулятор и готовые алгоритмы здесь не реализованы.

## Цели архитектуры

- Каждый участник может разрабатывать модуль независимо.
- Все реализации одного типа соблюдают единый контракт входов и выходов.
- Реализации можно переключать конфигурацией, не переписывая `main`.
- Общие типы данных и протоколы находятся отдельно от алгоритмов.
- Экспериментальные решения можно сравнивать, не смешивая их с основной версией.

## Сценарий верхнего уровня

1. Scout получает кадры/наблюдения, находит участки и оценивает число маркеров по цветам.
2. Selector выбирает участок по согласованному критерию (по умолчанию — максимум красных маркеров).
3. Coordinator передаёт выбранную цель Rover.
4. Rover доставляет Striker в заданную точку и подтверждает готовность.
5. Striker получает команду на запуск и выполняет обработку целевых красных маркеров.
6. Система сохраняет события, результаты и причины завершения.

Фактические полётные команды, ROS 2-топики и формат сообщений с веб-симулятором определяются после согласования интерфейсов с организаторами.

## Единый контракт

Модули должны зависеть от типов из `autonomy.contracts`, а не импортировать внутренности друг друга.

| Модуль | Вход | Выход |
|---|---|---|
| `drone_scout` | `ScoutInput` | `ScoutOutput` |
| `target_selector` | `SelectionInput` | `SelectionOutput` |
| `rover` | `RoverInput` | `RoverOutput` |
| `drone_striker` | `StrikerInput` | `StrikerOutput` |
| `communication` | `Message` | `MessageResult` |

Каждая реализация должна предоставлять одинаковый публичный метод `run(input) -> output`.
Временные данные, модели ML и внутренние классы остаются внутри реализации.

## Как добавлять альтернативные решения

Предпочтительный вариант — отдельная ветка на участника/эксперимент:

- `feature/scout-yolo-v1`
- `feature/scout-color-hsv`
- `feature/rover-path-planner-a`
- `feature/striker-approach-b`

После проверки реализации можно перенести в `src/autonomy/modules/` или выделить в отдельный пакет.
Не создавайте файлы `drone_scout_final_final.py`: используйте Git-ветки, коммиты и pull request.

Если нужно хранить несколько реализаций одновременно, используйте каталог по типу модуля:

```text
implementations/
  scout/
    baseline/
    hsv_detector/
    yolo_detector/
  rover/
    baseline/
    planner_a/
  striker/
    baseline/
    approach_b/
```

В таком случае все реализации должны проходить один и тот же набор контрактных тестов.

## Быстрый старт

Требуется Python 3.11 или новее.

```bash
python -m venv .venv
# Linux/macOS
source .venv/bin/activate
# Windows PowerShell
# .venv\Scripts\Activate.ps1

python -m pip install -e ".[dev]"
python -m pytest
```

`main.py` пока является точкой сборки/запуска и намеренно не содержит реального управления аппаратами. До подключения оборудования он не запускает полёты.

## Правила интеграции

1. Сначала согласуйте контракт и единицы измерения.
2. Не меняйте общий контракт без обсуждения и обновления документации/тестов.
3. Не храните секреты, токены или личные данные в Git.
4. Логи и тяжёлые артефакты моделей не коммитьте без необходимости; используйте `.gitignore` или Git LFS по решению команды.
5. Алгоритмы должны сообщать о невалидных входах и ошибках явно, а не возвращать фиктивный успех.
6. Аппаратные действия должны быть изолированы в адаптерах, чтобы алгоритмы можно было тестировать отдельно.
