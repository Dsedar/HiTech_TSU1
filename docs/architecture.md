# Архитектура системы

## Слои

1. **Contracts** — неизменяемые типы входов/выходов, статусы, общие единицы измерения.
2. **Modules** — взаимозаменяемые алгоритмы; не должны напрямую управлять SDK оборудования.
3. **Adapters** — интеграция с ROS 2, API веб-симулятора, камерами, телеметрией и транспортом сообщений.
4. **Orchestration (`main.py`)** — связывает выбранные реализации, управляет этапами сценария и обработкой ошибок.
5. **Observability** — структурированные события, тайминги, метрики и отчёт попытки.

## Направление зависимостей

`main/orchestrator → module protocols → contracts`

Адаптеры преобразуют внешние сообщения в типы контрактов и обратно. Алгоритмы не должны зависеть от конкретного транспорта, SDK или формата API веб-симулятора.

## Почему `run(input) -> output`

У каждого типа модуля один публичный метод с типизированным входом и выходом. Это позволяет:
- запускать реализации через один registry;
- прогонять одинаковые тесты для всех вариантов;
- сравнивать метрики;
- заменять реализацию через конфигурацию.

Длительные действия и асинхронные циклы можно будет добавить позже отдельным контрактом (например, `start/stop` или `async run`), если этого потребует API оборудования. Не смешивайте синхронный и асинхронный интерфейсы внутри одного типа модуля.

## Рекомендуемый жизненный цикл сценария

`IDLE → SCOUTING → TARGET_SELECTED → ROVER_DELIVERY → STRIKER_READY → PROCESSING → COMPLETE`

Любой этап может перейти в `FAILED` или `ABORTED`. Переходы, тайм-ауты и условия безопасной остановки должны быть описаны отдельно до интеграции с реальным оборудованием.
